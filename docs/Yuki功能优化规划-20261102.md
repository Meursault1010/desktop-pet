## 1. 使用方式与全局约束

开工任何一张卡片前，先确认这四条不会被破坏：

## 3. AI 助手能力

### OPT-01 对话持久化与会话管理（P0 · 收益高 / 代价中）｜已实现 2026-11-02

现状与证据

- 对话只有内存里一条会话：组件级 `session` 数组，`AssistantWorkspace.tsx:76` 裁到最近 10 条、总量 3800 字；主进程再限 16 条、14000 字（`assistant.cjs:20,26`）。退出软件即清空，UI 也如实写着「对话记录：仅本次运行保留」（`AssistantWorkspace.tsx:92`）。
- 无会话列表、无重命名、无删除单条，只有一个清空整条会话的按钮（`AssistantWorkspace.tsx:92` 的 Trash2，点击即 `session=[]`）。
- 附件缓存同样是内存 Map，最多 24 条，重启失效（`attachments.cjs:6,26`）。

目标

让「雪记得我们聊过什么」在重启后依然成立，并把单条会话升级成可管理的会话列表。

改动要点

- 主进程新增会话存储（沿用现有设置目录的写入方式，与 `workbench-config` 同层），字段：会话 id、标题、创建与更新时间、消息数组、所用模型标识。
- 消息裁剪从「丢弃」改为「落盘保留、按需取最近 N 条进上下文」，发给模型的窗口仍然保持 16 条 / 14000 字上限，不放大请求体。
- 渲染端加会话侧栏：新建、切换、重命名、删除；当前会话 id 持久化。
- 卡片里那句 UI 文案随能力同步更新，避免说明与实现不符。

验收标准

- 关闭工作台再打开，最近一次会话的消息与顺序完整恢复；退出应用再启动同样恢复，且**不需要用户先开启任何开关**（默认持久化）。
- 新建第二个会话后切回第一个，两边内容互不串。
- 单次发给模型的消息条数与总字数仍不超过 `assistant.cjs` 现有校验；超限时报错文案保持可理解。
- 会话文件损坏或不可读时能降级为「新会话」，不阻塞聊天与桌宠。

测试矩阵

- 新增 `electron/tests/conversations.test.cjs`：写入/读取/裁剪/迁移旧内存数据/坏文件降级。
- 扩展 `electron/tests/assistant.test.cjs`：上下文窗口上限不因持久化而放宽。
- `--smoke-test` 增加一组「重启后会话仍在」。

非目标与风险

- 不做自动摘要、不做向量检索、不把对话写进长期记忆。
- 风险在磁盘增长与隐私：会话含用户原文。按 2026-11-02 决策**默认开启持久化**，同时提供「只保留本次运行」开关与「清空全部会话」入口，会话文件放在设置同目录、不新增对外同步。

依赖：无。建议与 OPT-02 同一批做。

### OPT-02 消息级操作与富文本渲染（P0 · 收益高 / 代价中）｜已实现 2026-11-02

现状与证据

- 正文用 `<p>{item.content}</p>` 直接输出纯文本（`AssistantWorkspace.tsx:86`），模型返回的 Markdown 会原样露出星号和井号。
- 列表用数组下标当 key（同文件 `key={i}`），且每个 delta 都触发 `scrollIntoView`（`AssistantWorkspace.tsx:68`）。
- 发送失败只回滚草稿并显示错误，没有重试入口（`AssistantWorkspace.tsx:91` 的 composer 只有停止与发送）；模型侧错误文案已经明确建议「请重试」（`assistant.cjs:100,107`），但用户只能手打一遍。
- `package.json` 依赖只有 react/react-dom/radix/lucide/mammoth/pdf-parse，无任何 Markdown 或净化库。

目标

每条消息可复制、可重新生成、可删除；失败可一键重试；回答里的 Markdown 正确显示且不引入 XSS。

改动要点

- 消息加稳定 id（`crypto.randomUUID`，与附件 id 同风格），列表 key 从下标换成 id。
- 每条回答 hover 出「复制 / 重新生成 / 删除」；重新生成复用上一条 user 消息与其附件，不重复计费式追加历史。
- 失败态（停止、超时、模型错误）保留草稿与附件，提供「重试」按钮，重试前明确提示会覆盖刚才那条。
- Markdown 渲染：优先自写一个只支持粗体、行内代码、代码块、列表、链接、标题的最小渲染器，避免新增依赖；若引入第三方库需一并加净化与体积核对。链接点击必须走现有 `host.openExternal`（`AssistantWorkspace.tsx:86` 已是这个模式），不允许 `<a href>` 直接导航。

验收标准

- 贴一段带代码块与列表的模型回复，渲染正确、可复制、复制内容与源文本一致。
- 重新生成一次，历史条数不变、上下文不含上一条回答。
- 断网或模型未加载时点发送，草稿与附件仍在，点重试能成功。
- 恶意输入 `![x](javascript:...)`、`<script>` 不会执行或产生页面内导航。
- 流式期间滚动位置不被强行打断（用户上滑阅读时不再被拽回底部）。

测试矩阵

- 渲染器纯函数测试放 `frontend/tests/markdown.test.mjs`（与 `actionTimeline.test.mjs` 同风格，`node --experimental-strip-types --test` 可直接跑）。
- 消息操作走 `electron/tests/assistant.test.cjs` 的取消与错误分支。
- 真实截图：长回答、代码块、错误态三种各一张。

非目标与风险：不做 LaTeX 公式、不做语法高亮主题。风险是渲染器与现有 `chat-turn` 样式（`assistant.css`）冲突，需按当前设计令牌调整而不是新增视觉层。

依赖：与 OPT-01 同批。

### OPT-03 附件真正交给视觉模型并允许云端（P0 · 收益高 / 代价低）｜已实现 2026-11-02

现状与证据

- `attachments.cjs:15` 先做本地 OCR，`:37` 把 `recognition==='ocr'` 的图片**从 image payload 里过滤掉**，`:38` 只把剩下的图作为 `image_url` 发出。结果是：只要 OCR 成功，即使当前模型是视觉模型，它也只看得到 OCR 文字，永远看不到图。
- 说明文案与实现一致地保守：「图片通过本地 OCR 提取中英文文字……不能识别物品或场景」（`AssistantWorkspace.tsx:92`）。
- 附件被硬性限制为本机端点：`assistant.cjs:65` 对非 `localhost/127.0.0.1/[::1]` 直接抛「附件仅发送给本机模型」。
- 附件文字总量 24000 字符上限（`assistant.cjs:68`），单文件 10 MB、每条消息最多 4 个（`attachments.cjs:10,30`）。

目标

图片附件按用户选择走「OCR 文字 / 原图 / 两者都给」，让视觉模型能识别场景与物品；云端在用户明确知情后也可以带附件。

改动要点

- `Attachments.add` 保留 `data`（base64）与 `text` 并存，不再互斥；`contentWithAttachments` 依据每张图片的模式决定拼接文字、发图、或两者并发。
- 附件卡片上给每张图片一个识别模式选择，默认「文字 + 原图」；无视觉能力的模型选中后由主进程校验并提示换模型，沿用 `assistant.cjs:85` 那句「图片还需要视觉模型及对应视觉组件」。
- 云端允许带附件（2026-11-02 决策）：复用现有「选择云端即内容交给所选服务」的告知边界（PRODUCT.md），首次向云端发送带附件的消息时弹一次确认，可在设置里关掉再次询问；附件卡片上要看得见「将发送至 <当前服务>」。不做静默上传。
- 更新 UI 文案，去掉「不能识别物品或场景」的绝对表述。

验收标准

- 用本机视觉模型发一张「桌面截图问她在哪」，回答能描述画面内容而不只是复述 OCR 文本。
- 同一张图切「仅 OCR 文字」时，请求体里不含 `image_url`；切「原图」时不含 OCR 文本注入。
- OCR 完全失败的图片仍作为 `image_url` 发出（现在这条路径已存在，需回归确认没被改坏）。
- 云端带附件时先出现明确告知，拒绝后草稿与附件不丢。

测试矩阵

- 扩展 `electron/tests/attachments.test.cjs`：三种模式的 payload 结构、OCR 失败回落、大小与条数上限不变。
- 扩展 `electron/tests/assistant.test.cjs`：非本机端点带附件的授权分支与拒绝分支。
- 真机验证一次视觉模型问答，留对话截图。

非目标与风险：不做图片预处理、不做 OCR 引擎替换、不改 10 MB/4 个上限。风险是带原图后请求体显著变大，本地端上下文超限概率上升，需实测一张典型截图的 token 占用。

依赖：无。可当天独立开工，是本轮性价比最高的一项。

### OPT-04 取消记录：删除联网搜索（2026-11-02 已执行）

决定

不加深、不接服务商，**整条联网检索通路删除**。雪只基于用户发送的内容、附件文字与当前模型回答，聊天过程不再为获取外部资料发起任何网络请求。PRODUCT.md 的对应边界已同步改写。

理由（本机实测，2026-11-02）

- 现状实现依赖 `https://api.duckduckgo.com/`，但这台机器上 DDG 三个端点（api / html / lite）全部 12 秒超时，域名被解析到 103.252.115.59 这类污染地址——功能实际上从未可用。
- 候选服务商可达性也不理想：`api.search.brave.com` 超时不通；`api.tavily.com` 可达但未带 key 的握手就花 5.3 秒；Exa、AnySearch 域名可达（2.7～3.0 秒）。海外 SaaS 的"免费额度"在这台机器上要先过网络这一关。
- 唯一又快又稳的是直接抓 `cn.bing.com` 结果页（普通 HTTP、不渲染 JS，0.49 秒返回 98 KB、解析出 7 条真实结果），但那属于SERP 抓取：静默坏、风控验证码、条款禁止、维护不可预测、且要在「渲染层默认全禁网络」这条安全线上开洞（`electron/main/index.cjs:207`）。权衡下来不值得为桌宠养一条解析器。

已删除的内容

- 模块与测试：`electron/main/web-search.cjs`、`electron/tests/web-search.test.cjs` 整文件移除。
- 主进程：`assistant.cjs` 的 `searchWeb/contextForSearch` 引用、`chat()` 的 `webSearch` 入参、搜索调用与 `searchResult/searchError` 变量、system 提示里的 `contextForSearch(searchResult)` 拼接、返回值中的 `sources` 与 `webSearchError` 字段；`index.cjs` 里 `yuki:ai-chat` 的 `webSearch` 注入。
- 渲染层：`src/host/types.ts` 的 `aiChat` 入参与返回类型、`AssistantWorkspace.tsx` 的 `Source` 类型与 `sources` 字段、`webSearch` 状态、输入框旁的「联网搜索」复选框、回答下方的来源卡片、`webSearchError` 提示；右侧「联网 / 语音 / 工具 · 未启用」改为「语音 / 工具 · 未启用」。`assistant.css` 删掉 `.web-search-toggle` 与 `.chat-sources` 五条规则。
- 边界说明：PRODUCT.md 中「AI 助手的联网搜索由用户在发送消息前主动开启…」一条改为不提供联网检索的表述。

备份与验证

- 删除前的完整副本在 `console-v2/backup-websearch-20261102/`（这批代码当时尚未提交，Git 里没有第二份）。
- 删除后 `npm run build`（tsc + vite）通过；`npm test` 94/95 通过，唯一失败是既有无关项 `all catalog posters and atlases are packaged and schedules match`（`assets/actions/play-lean/` 缺 `poster.webp`，与本次删除无关，删除前即失败）。未启动实机应用核对界面（单实例锁会干扰正在运行的雪）。

规则

- 不要以「加深搜索」「换个服务商」「用浏览器抓」为名恢复这条通路；若要重新引入，需要单独决策并先解决本机可达性与网络白名单设计。
- 8.1～8.3 保留为调研记录，只作背景，不代表待办。

### OPT-05 AI 日报与提醒浮窗联动（P1 · 收益高 / 代价低）

现状与证据

- 事件总结只是计数文案，末尾明写「尚未采集应用使用历史，无法总结全天应用使用数据」（`WorkbenchTools.tsx:18`）。
- 但真实数据已经在主进程攒着：事件流上限 20 条、10 秒内同类去重（`desktop-services.cjs:49-50`），加上 `useWorkbench.ts` 里的专注完成数、待办、健康提醒状态。
- 未提交改动刚做了自绘桌面提醒浮窗（`electron/main/index.cjs:45-58` 的 notification 窗口），日报可以直接投递到那里。

目标

用本次运行已经发生的真实数据，让雪生成一段短日报，可在工作台查看、可推到提醒浮窗，并按日期跨天留存成可回看的历史（2026-11-02 决策）。

改动要点

- 主进程加一个 `daily-summary` 聚合器：本次运行事件流、已完成专注段数、已到期与已完成待办、陪伴时长。
- 调一次模型生成 80–150 字中文小结，模板兜底（模型不可用时输出计数版），保持「不虚构未做的事」的提示约束，参照 `assistant.cjs:13` 那句生活阶段提示的写法。
- 触发方式：工具页手动按钮优先；定时推送默认关，开启后走提醒浮窗。

验收标准

- 日报里的每个数字都能在事件流/专注/待办里对应到真实记录；无数据时输出明确的「今天还没有记录到活动」。
- 模型不可用时不报错，回落模板文案。
- 生成过程不采集任何窗口标题或应用使用轨迹，与 PRODUCT.md 的边界一致。
- 跨天可回看：第二天仍能看到前一天生成的日报；单条删除后不再出现；关闭留存开关后不再生成新文件，已有历史保持可删。
- 推送时不抢焦点，点浮窗跳工作台对应区块。

测试矩阵

- 新增 `electron/tests/daily-summary.test.cjs`：聚合正确性、空数据、模板兜底、超长截断。
- 复用提醒浮窗已有测试路径，补一条「浮窗可承接日报文案」。

### OPT-07 计时与提醒迁到主进程（P0 · 收益高 / 代价中）｜已实现 2026-11-02

现状与证据

- 专注结束是渲染端 `window.setTimeout`（`useWorkbench.ts:50`，即 `useEffect` 中 `setTimeout(()=>completeFocus(end), end-Date.now()+50)`）；待办到期与健康休息提醒跑在渲染端 1 秒 tick 里（`useWorkbench.ts:52` 起的 tick，含 `todos.filter(...due<=now)` 与 `rest.next` 判断）。
- 快照拉取也是渲染端 3 秒 / 15 秒定时器（`useWorkbench.ts:38`），且 `if(!document.hidden)` 才刷新。
- 专注、待办、健康状态存 localStorage（`useWorkbench.ts` 的 `saveStore`），失败只提示「本地存储不可用」。

目标

工作台窗口关闭或最小化后，专注、待办、健康提醒照常触发。

改动要点

- 计时权威移到主进程：专注结束、待办到期、休息提醒由主进程定时器与真实时钟驱动，事件通过 IPC 推给渲染端。
- 渲染端只做显示与操作，不再持有到期判定；保留现有 `notify` 语义，落到新的提醒浮窗。
- 状态持久化从 localStorage 迁到主进程配置存储，与设置同处，避免「清浏览器数据即丢」。存的必须是**绝对时间戳**（`end`、`mode`、`completed`、待办的 `due/notified`、健康提醒的 `next`），重启据此按真实时钟续算；现在 `useWorkbench.ts` 里 `remaining` 是秒数倒计时，迁移时不能沿用相对值。
- 休眠唤醒策略要明确：错过的提醒不补发（与桌宠作息逻辑「不补播错过的活动」一致）。

验收标准

- 设一段 1 分钟专注，关闭工作台窗口，到时收到浮窗提醒并且完成计数 +1。
- 待办到期时同样在窗口关闭状态下触发；同一条目不重复提醒。
- 系统睡眠 10 分钟再唤醒，不产生成串的补发提醒。
- 专注进行中退出应用再启动：剩余时间按真实时钟继续（决策已定），只有用户主动取消或已完成才归零；若期间已经超时，重启后立即补一次「这段专注结束了」的提示并计入完成段数，但**不因此产生成串提醒**。

测试矩阵

- 新增 `electron/tests/timers.test.cjs`：注入假时钟覆盖到期、去重、休眠、重启恢复。
- `--smoke-test` 增加「关窗后提醒仍达」的一组断言。

非目标与风险：不做多设备同步、不做日历集成。风险是主进程与渲染端两份状态短暂不一致，必须以主进程为唯一权威并在 UI 显示同步延迟。

依赖：提醒浮窗那批未提交改动落地后开工。

实现记录（2026-11-02）：新增 `electron/main/workbench-timers.cjs`（`WorkbenchTimers`，绝对时间戳 + 单一定时器 + 原子写 `workbench-timers.json`）、IPC `yuki:workbench-timers` / `yuki:workbench-timers-set` 与 `yuki:workbench-timers` 推送、`host.workbenchTimers*` 三个方法；`useWorkbench.ts` 删掉 1 秒 tick、`window.setTimeout` 与 localStorage 权威（localStorage 只留作首屏缓存，并做一次性迁移）。提醒经 `index.cjs` 的 `notifyDesktop()` 落到已落地的自绘浮窗，`desktopServices` 与计时共用同一条通路。与卡片的差异：休眠只挂 `powerMonitor` 的 suspend/resume（锁屏不暂停，避免把提醒静默吞掉）。顺带修掉一个真实缺陷：快捷工具投影响应只认 15/25/45/60 四档专注时长且 `remaining≤3600`，用户手填 30 分钟或 1 小时会让桌面浮窗静默失效——`quick-tools.cjs` 与 `pet_quick_tools.py` 两份校验同步放宽为 1–180 分钟、`remaining≤10800`。

- 临时前置逻辑每 250ms 轮询 `GetForegroundWindow`（`pet.py:732-733` 连接 `check_temporary_foreground`，取句柄在 `pet.py:999-1003`）。

目标

用系统事件替代常驻轮询，既省 CPU 也补齐层级需求文档的验收项。

改动要点

- 装 `SetWinEventHook`（前台切换事件），回调经消息循环转 Qt 信号，驱动 `temporary_foreground` 判定与解除。

验收标准

- 拖动、菜单、睡眠、专注、音乐等既有优先级不被破坏。
- 需求文档第 9 节「验收标准」逐条可勾。

测试矩阵

### OPT-12 遮挡判断从矩形近似升级（P2 · 收益高 / 代价高）

现状与证据

- 可见性判断是 Z 序遍历 + 矩形相交，注释自己写明「Conservative occlusion」（`desktop_icons.py:255-266`），过滤掉不可见、最小化、透明分层覆盖窗。
- 宠物窗口的前后层级遮罩也只是把窗口矩形从 `QRegion` 里减掉（`patrol_depth.py:99-111`）。
- 后果：带圆角、阴影、异形或半透明的窗口会被当成完整矩形，巡逻因此过早放弃可用位置，停靠点判断也偏保守。

目标

用窗口精确区域替代外接矩形，让「看起来空着的地方」真的可用。

改动要点

- 取窗口 Region（DWM 扩展边框 + 可见区域），生成精确遮挡集合；不可用时按现状回落并记录。
- 巡逻选点、图标支撑点、上沿/侧边停靠共用同一套遮挡查询，避免各模块各自近似。
- 建立离线 QA 场景（固定窗口组合的截图与预期可用区域），先量化当前误差再改。

验收标准

- 构造一个异形/大圆角窗口场景，雪的可用落点数量上升且不落在窗口实体上。
- 100 次巡逻选点的失败原因统计中「遮挡误判」明显下降。
- 单次遮挡查询耗时不进入鼠标或物理回调线程，UI 帧率无可测下降。

测试矩阵

- 新增 `console-v2/test_occlusion_region.py`（合成窗口矩形/区域夹具，断言可用点）。
- 扩展现有 `patrol_depth` 相关测试覆盖 Region 分支与回落分支。

非目标与风险：不做像素级实时抓屏判定（成本高且涉隐私）。风险显著：DWM 边界在不同 DPI、Win11 家庭版与远桌下表现不一；代价是本轮最高，建议单独开一个会话推进。

依赖：OPT-13/14 的稳定枚举先行。

### OPT-13 多屏与多桌面视图枚举（P1 · 收益中 / 代价中）

- 出屏横向穿越在「外侧还有别的显示器相交」时直接拒绝（`patrol_passage.py:23-26`），多屏事实上不参与。

目标

副屏桌面可被感知与使用，并按已确认策略允许她跨屏走动。

改动要点

- 屏幕几何或 DPI 变化时重建缓存（`QGuiApplication.screensChanged`）。
- 跨屏行走策略已定（2026-11-02 允许）：去掉 `patrol_passage.py:23-26` 这条「外侧还有别的显示器相交就拒绝出屏」的守卫，改为按屏幕几何接续——从 A 屏边走出后在 B 屏对应侧复位，层级切换仍遵守「完全横向走出屏幕后才换层」的既有规则。
- 这条要同步改写 PRODUCT.md 的边界描述（现在写的是巡逻「不跨屏」与「多屏出屏避免相邻屏幕暴露隐藏位移」），否则文档与行为分叉。

验收标准

- 双屏环境（主 + 副）下，副屏桌面图标能被识别为支撑点并可靠近。
- 跨屏走动实测：从主屏走到副屏全程有步行动画、不出现中途传送或半身在两屏之间；从副屏返回同样成立。
- 拔掉副屏后不残留幽灵图标，雪的当前位置若在被移除屏幕上会被安全拉回。
- 主屏行为与改动前一致（回归既有用例）。

测试矩阵

非目标与风险：不做跨屏跟随第三方窗口。风险是主屏/副屏 DPI 混排（125% + 100%）下坐标换算出错，必须用物理坐标统一。

依赖：无，但需要双屏实机环境。

### OPT-14 图标扫描时效与拖放吸附（P1 · 收益中 / 代价中）

现状与证据

- 一次 shell 扫描约 250ms 的 Python 开销，代码注释直接写明「每 0.7 秒轮询会让工作线程长期抢掉接近一个核、并让突发点击变迟」，因此观察轮询退到 2500ms（`icon_sleep.py:158-162`），拖放只接受 3 秒新鲜度守卫内的扫描。
- 后果：桌面刚变动（新增/移动图标）后的短时间内，拖放吸附可能用旧位置；同时这一路扫描仍在持续消耗 CPU，与 OPT-08 的减负目标同源。

目标

扫描更快、结果更新鲜，拖放吸附不吃旧数据。

改动要点

- 扫描改增量化：只在桌面视图内容变化或前台/壁纸窗口变更时重扫，其余时候读缓存；把「必扫 250ms」变成「偶发」。
- 给缓存加版本与时间戳，超阈值未刷新时拖放走「不吸附」而不是吸附到旧位。
- 与 OPT-08 的 PowerShell 常驻子进程区分开，两侧都要有失败可见性。

验收标准

- 桌面图标变动后 500ms 内缓存更新；无变动时扫描调用次数下降。
- 拖放到已被删掉的图标位置时不吸附、不错位。
- 松手响应耗时保持现有的毫秒级（参照 `qa/drag-preview/release-after.json` 的测法，本次重新采样）。

测试矩阵

- 新增 `console-v2/test_icon_scan_freshness.py`：假时钟下断言增量刷新、过期拒绝。
- 复用 `audit_desktop_icons.py` 做一致性核对。

非目标与风险：不改吸附交互语义（仍受「拖放即时吸附」开关控制）。风险是变化监听在 OneDrive 同步等高频场景下退化为持续扫描，需要节流。

依赖：与 OPT-13 同批更省事。

### OPT-15 停靠候选扩展（P2 · 收益中 / 代价中）

现状与证据

- 被动侧边互动只选非全屏、非最大化窗口的真实左右边框；屏幕边、任务栏、窗口正文都不进候选（`docs/Yuki行为逻辑总览-20261024.md:540`）。

- 好奇度评分「目前只作为内部状态展示，不直接参与候选评分或冷却计算」（`docs/Yuki行为逻辑总览-20261024.md:443`）。

目标

改动要点

### OPT-16 让停靠停留时长真正生效并删除无用开关（P2 · 收益中 / 代价低）

现状与证据

- 边缘附着的默认值有五个字段：`DEFAULTS=dict(enabled=False,windows=True,screens=True,corner='right',delay=8)`（`edge_attachment.py:16`），`delay` 校验 2～60 秒、错误文案是「停留时间应在 2～60 秒之间」（`:24`）。
- `delay` 在运行时只被写进 `self.until`（`:57` 初始化、`:80` 释放冷却、`:174` 归零），而 `self.until` **全文只被赋值、从不被读取**——`tick()` 读的是 `next_move` 与 `hold_until`（`:286`）。也就是说这个"停留时间"设置现在完全不生效。
- `enabled` 的唯一实际作用是 `release()` 末尾 `if not self.options['enabled']: self.timer.stop()`（`:85`）；但 `attach()` 无条件 `self.timer.start()`（`:182`），且 `tick()` 在没有支撑时立刻返回并注释写明「No autonomous search: only follow an already established grip.」（`:250-252`）。关掉它既不会断开已建立的跟随，也不会阻止停靠，只是让空闲定时器停下。
- 界面上不出现：`IconSleep.tsx:50-52` 只渲染 `windows / screens / corner`。但两个字段仍通过 `snapshot().options`（`:87`）回传前端、仍被 `configure_edge_attachment`（`pet_backend.py:485-486`）接受写入，`validated()` 还会因未知 key 报错（`:19`）——属于「可读可写、无入口、无效果」。
- 来源是 2026-10-17 那次收敛：「附着改为只通过手动拖放到边框或图标触发；移除后台自动寻找边缘，保留停靠后的窗口跟随、抓框爬行和即时吸附开关。旧设置即使曾开启自动寻找边缘，也不会主动停靠」（`CHANGELOG.md` 未发布 — 日常随机待机）。字段留下来了，行为语义没了。

目标

消除"用户设置能写进文件却对行为毫无影响"的状态，让边缘附着的开关与实际语义一致。

已定方向（2026-11-02）：**`delay` 改作它用并真正生效，`enabled` 删除。**

改动要点

- `delay` 变成「单次自主停靠的停留时长」，单位秒，沿用现有 2～60 校验。**默认值已定（2026-11-02）：均值 21 秒、±30% 抖动，正好覆盖现有的 15～28 秒表现**，滑块范围仍 2～60。
- 接到两个真实停留点，而不是新写一套计时：被动侧边互动的 `self.until = now+random.uniform(15,28)`（`pet_patrol.py:722`），以及窗口顶部玩耍停留 `random.uniform(15,35)`（`pet_patrol.py:1189`，后台场景仍走 `BACKSTAGE_HOLD` 不动）。
- 不要把随机完全消掉：以 `delay` 为均值取 ±30% 抖动（并夹在 2～60 内），保持「每次不太一样」的生活感；完全固定会让停留像定时器。
- 生效范围只限**自主与被动**停靠。手动拖放到边框或上沿的停留仍由用户行为决定；`auto_snap`、「拖放即时吸附」与「自主窗口互动」三个既有开关的语义不变。
- UI 在 `IconSleep.tsx:47-53` 那组边缘附着选项里加一个 2～60 秒滑块，标签写「单次停靠停留时长」，说明写清「她自己去抓框攀爬或坐上窗沿时大概待多久」；沿用现有 `sleep-options` 卡片样式，不新建视觉体系。
- `enabled` 删除：从 `DEFAULTS`、`validated()`、`settings.ini` 读写、`snapshot()`、前端 `EdgeOptions` 类型与 `configure_edge_attachment` 允许集里一并移除；配置里残留的旧键加载时忽略且不报错。`release(cooldown=…)` 的内部冷却改成显式常量并注释，不再伪装成用户设置。

验收标准

- 设成 5 秒与 60 秒各实测一次：被动侧边攀爬与顶部停留的实际时长随设置变化、落在 `delay`±30% 内且不越界 2～60；固定随机种子结果可复现。默认 21 秒时实测区间应覆盖 15～28 秒。
- 停留结束后的行为不变：仍沿支撑爬下或自然松开，不出现到点瞬移脱离。
- 关闭「自主窗口互动」后不产生新的自主停靠，`delay` 不参与任何自主判定；手动拖放停靠不受该设置影响。
- 滑块改动即时生效、不需要重启，重启后值保留。
- 代码与配置中不再出现 `edge_attachment/enabled`；`configure_edge_attachment` 对未知 key 仍拒绝，`delay` 越界的错误文案保持可读。

测试矩阵

- 扩展 `console-v2/test_edge_attachment.py`：`validated()` 字段集变化、旧配置含 `enabled` 时被忽略、`delay` 边界值。
- 新增假时钟用例，断言 `pet_patrol.py:722` 与 `:1189` 两处停留时长来自配置而非硬编码常量。
- 回归既有 `test_window_edges.py` 与拖放吸附用例。

非目标与风险：不改吸附交互语义，也不给每类动作单独设时长。风险一，停留时长变成用户可控后与作息、鼠标避让、拖动优先级的冲突概率上升，既有 13 类阻塞优先级必须原样保留；风险二，默认值抬到 20 秒会让「她在窗口边挂很久」的观感变强，需真机确认是否合意。

依赖：无。与 OPT-11 同批最省事（两处都动 `edge_attachment.py`）。

### 8.1 联网搜索的全部方式（调研存档，功能已删除）

以下为决策当时的方式盘点，保留备查，不代表待办。当日本机实测的可达性结论：DDG 三端点全部超时、Brave API 不通、Tavily 与 Exa、AnySearch 可达但握手 2.7～5.3 秒、`cn.bing.com` 普通 HTTP 0.49 秒可抓到结果——最终因此选择整条删除，见 OPT-04 取消记录。

当时按「要不要注册、能拿到什么、代价在哪」分档如下。

- **0 · 摘要接口（现状）**：DDG Instant Answer。零配置、不要 key，但它只是搜索引擎的「摘要卡片」，不是搜索结果页；没有卡片的问题就返回空。只适合当兜底。
- **1 · 免 key 的结果页抓取**：直接抓 Bing / 百度 / 搜狗的结果页 HTML 再解析（Python 侧的 `ddgs` 库就是这类）。好处是完全不用注册；坏处是对方改版就坏、容易被限流封 IP、稳定性与合规都在灰区，不适合作为主力，适合当第 2 档不可用时的临时回落。
- **2 · 外部搜索服务 API（已选）**：注册拿 key，一次 POST 换回结构化的标题、URL、摘要，好的还直接给清洗过的正文。稳定、有文档、有明确的超额行为（通常 429 停用而不产生账单）；代价是要注册、可能绑卡、免费额度会烧完。候选见 8.2。
- **3 · 自建聚合搜索（SearXNG）**：自己跑一个开源聚合服务，由它替你去问多个引擎并返回 JSON。免费、隐私最好、国内直连不受海外服务商影响；代价是多一个必须常开的服务，雪联网时它得在线，你要负责维护。本机 WSL2 可以跑。
- **4 · 让模型自己去搜**：三种深浅不同的做法。
  - 4a 云端模型自带联网（DeepSeek、通义、Kimi 一类在服务端内部检索）：实现最省事，只要在请求里打开对方提供的参数；但你拿不到可控的来源列表，且这部分已商业化（DeepSeek 自研搜索与抓取 2026-11-01 起计费，千次约 5 元）。可作为「零配置省事档」并存。
  - 4b 工具调用（function calling / tool use）：把搜索做成一个函数交给模型，它自己决定查不查、查什么、查几轮。上限最高，但要求模型支持且够强（本地 Qwen3.8-4B 这类小模型的调用格式经常出错），还要实现「模型→工具→再回模型」的循环。工程代价明显高于第 2 档。
  - 4c 让 Yuki 变成 MCP 客户端去调搜索服务：与 4b 同类但多一层协议，为桌宠不值。
- **5 · 固定数据源（不做通用搜索，但对桌宠最实用）**：天气、新闻 RSS、GitHub 仓库、热搜这类点对点接口。不是搜索，可你日常那几类「今天天气怎么样」「有什么新闻」用它更稳、更快、零注册——尤其天气有免 key 的公开接口（Open-Meteo、wttr.in），能顺手替掉现在「必须手输城市名才出数据」的做法。建议独立成一条小功能，与第 2 档不冲突。
- **6 · 本地知识检索（RAG）**：先把你要她了解的网页或文档抓下来建索引，提问时从本地找。离线可用、隐私最好；但不解决「最新信息」，还要你维护语料。
- **7 · 借本机浏览器**：调用已装的 Edge/Chrome 打开搜索页再解析，甚至用你已登录的账号能看到的内容。能力最强，代价也最高：实现与稳定性成本大，而且「雪偷偷动了我的浏览器」这种体验风险需要你先接受。三条子路线的可行性拆解见 8.3。

横向结论：主力走第 2 档；第 5 档作为独立便宜功能优先做；第 0/1 档留作降级；第 3 档取决于你愿不愿意养一个服务；4a 在你用云端 DeepSeek 时可以当「零配置档」并存；4b/4c/6 本轮不建议；第 7 档里只有 7a 值得作为「你不注册 key 时的备用 provider」保留在纸面上，7b/7c 暂缓（依据见 8.3）。

### 8.3 第 7 档「本机浏览器」可行性拆解（存档）

- **7a 用 Electron 自带的隐形 BrowserWindow 抓结果页**（完全不碰你的浏览器）。阻塞点很实在：本应用对网络是「默认全禁」——`session.defaultSession.webRequest.onBeforeRequest` 只放行 `yuki://app/` 与 `data:`（`index.cjs:207`），webContents 权限也全部拒绝（`:205-206`）。要开这条路必须新建独立 partition session 并只对它放宽、只允许搜索引擎域名、用完即关，等于在项目里最强的那条安全约束上打一个洞，得先设计再动手。优点是 Chromium 能跑 JS，比第 1 档纯 fetch 稳；仍躲不开站点改版与反爬。可行性中-高，代价中。
- **7b 复用本机浏览器的登录态**（扩展 + 本地消息通道）。要克服：写并长期维护一个扩展（Edge 可侧载或上商店，Chrome stable 忽略 `--load-extension`）；扩展与 Yuki 之间的本地通道必须鉴权，否则本机任意进程都能借你的登录态发请求；解析规则放扩展还是放主进程；浏览器自动更新导致扩展失效。可行性中，工程与维护面比第 2 档大数倍，只有「必须登录才看得到」的内容（内网、私有仓库、你的邮箱）才值得开。
- **7c 用 CDP 附着正在运行的浏览器**。硬阻塞：Chrome/Edge 自 111 起不允许在默认用户目录上开 `--remote-debugging-port`，要复用 profile 只能整体复制用户目录（含 cookies，敏感且体积大）或让你以调试模式自己启动（不现实）；已在运行的浏览器有单实例锁，附加不上；调试端口在本机无鉴权，风险最高。可行性最低。
- **Python 侧走不通**：`requirements.txt` 只有 PySide6、PyAudioWPatch、opencv-python-headless，没有 QtWebEngine；要塞进去等于给已经 637 MB 素材的包再加几百 MB 运行时。
- **与既定目标冲突**：常驻浏览器进程意味着几百 MB 内存与 1～3 秒冷启动，和 OPT-08 要的「静置时后台基本静止」、以及「问一句马上答」都相反；崩溃与孤儿进程回收还得另做一套（现有 `sidecar.cjs` 只管 Python 侧车）。
- **体验与合规**：标签页乱跳破坏信任；藏后台发起请求你又看不见，必须做显式开关加「刚才用了你的浏览器」的回执。另外主流搜索引擎的服务条款普遍禁止自动化抓取结果页——第 2 档 API 存在的理由正在于此。
- **最低成本的折中**：不解析也不抓，只用已经在用的 `shell.openExternal` 把搜索结果页丢给系统浏览器，把「查」交回给你。零风险、零维护，但解决的是「她帮我打开看看」，不是「她自己会不会答」。

结论：7b/7c 本轮不做；7a 只作为备用 provider 保留，真要实施需要先解决独立 session partition 与网络白名单设计，不能顺手放宽全局策略。
